# Story 2.2: The non-blocking, resumable import job

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a lawyer who wants to keep working while four years of a *matter* import,
I want the job to run in the background and survive a crash without losing or repeating work,
so that a machine restart at hour six does not mean starting over.

**Scope in one line:** move the ingest work off the HTTP request onto a **PostgreSQL-backed Procrastinate job** (AD-6), and make each *pièce* an **idempotent, resumable, quarantinable, memory-bounded unit of work** committed against an **application-owned ledger** that is the sole authority for state and for the *processed-against-submitted* progress figure (AD-17) — with resume proven by an induced **SIGKILL** mid-unit and completion proven with a **poison unit**.

> **This story is LARGE and the work breakdown flags resumable ingestion as *likely underestimated*.** It is written as one story for traceability of the AD-17 contract; it may be split at implementation. Its load-bearing, non-obvious mechanics are the *pre-work attempt-counter commit* and the *independent quarantine transaction* — get those exactly right (Dev Notes).

> **This story does NOT build:** multi-format extraction / OCR (**2.3** — reuse today's `_extractor()` unchanged); container expansion changes (**2.4** — reuse today's `_expander()`); new `(content, matter)` identity semantics (**2.5** — reuse the existing deterministic `piece_id`); the *failure-register* UI, bulk retry, resolution surface (**2.6** — this story only *writes* register rows for the two new classes); the completion summary (**2.10**); the worklist / home (**2.11**); durable exclusion read-back and the permanent home denominator (**2.7**). Building any is a review-blocker.

## Acceptance Criteria

> **Given** a running *import job*, **When** the user does anything else, **Then** no screen is blocked and no modal shown, and progress is a persistent, collapsed, non-blocking indicator of *processed-against-submitted* (FR-2).
> **And** killing the worker mid-job and restarting resumes from the last committed unit — no indexed *pièce* re-indexed as new, no unprocessed *pièce* skipped — asserted with an induced kill at **three or more** points (FR-2; Procrastinate over PostgreSQL makes resume a transaction property, AD-5).
> **And** memory is bounded per unit of work: no single *pièce*, however large, need fit in memory whole, and a unit exceeding the bound enters the *failure register* as `resource-exhausted` rather than killing the worker.
> **And** *(failure path)* a poison unit that kills the worker is **quarantined** after a configured number of attempts, entered in the register with its class, and the job **proceeds and completes** — asserted with a deliberately poisonous unit.

1. **AC1 — The HTTP request enqueues and returns; it never does the work (AD-6, FR-2).** `POST /api/ingest-upload` — the browser onboarding gesture — **validates, authorises, durably records the submission, enqueues a job, and returns immediately** with a job handle — no extraction, no `store.save`, no blocking in-request. The uploaded bytes are spooled to a **durable** staging location (the request's `TemporaryDirectory` is gone on return), so a background+restarted worker can read them. *(Amended per the review, confirmed by Julian: the non-blocking guarantee is scoped to the onboarding gesture — the browser upload. The sibling `/api/ingest` is a server-local-folder path used only by the CLI and tests and stays synchronous — a deliberate, documented deviation; the user-facing gesture FR-2 names is the browser upload.)* Asserted by test: the endpoint returns before any *pièce* is committed (the corpus is still empty at return; it fills only after the worker runs).
2. **AC2 — The application-owned ledger is the single authority for state and progress (AD-17).** A new app-owned progress record (per *import job*: the frozen *submitted* count, and running counts of committed / failed / quarantined units, plus job state) is the **only** source of the *processed-against-submitted* figure. The Procrastinate job table is **never** read by any progress/read path. A `GET /api/imports/{job_id}` (or equivalent) status resource the SPA polls returns the ledger figure. Asserted by test: the progress figure is computed from the ledger, and the SPA gets a live count.
3. **AC3 — Each *pièce* is one idempotent unit keyed by identity; re-processing is a no-op that reports itself (AD-17, AD-8).** A unit commit uses the existing deterministic `piece_id` + `session.merge` idempotency; re-running an already-committed unit adds **no** duplicate *pièce*, and writes **no** second audit entry — it reports against the existing one (AD-6 idempotency-covers-audit). Asserted by test: driving the same unit twice leaves one *pièce* and one audit entry.
4. **AC4 — Resume from the last committed unit, proven by SIGKILL (AD-5, AD-17, FR-2).** Killing the worker mid-job and restarting resumes from the last committed unit — no indexed *pièce* re-indexed as new, no unprocessed *pièce* skipped. The **attempt counter is incremented in a transaction committed *before* the unit's work begins**, so an OS-level `SIGKILL` still advances it. Asserted **on the PostgreSQL leg** with an induced `SIGKILL` mid-unit at **three or more** points (the in-memory connector cannot reproduce crash-mid-transaction — it covers the resume-via-idempotency logic and the counter-before-work property via an induced exception; the durability claim is the Postgres-leg test).
5. **AC5 — A poison unit is quarantined in an independent transaction; the job completes (AD-17).** A unit that repeatedly kills the worker is **quarantined after a configured number of attempts**, entered in the register as its own entry (a new quarantine `ErrorClass`), and the job **proceeds and completes**. The quarantine transition and its register entry are committed in a transaction **independent of the failing unit's** — an exception handler that wrote inside the failing transaction would roll back with it and retry the poison forever (the exact failure AD-17 names). A unit whose attempt counter exceeds its bound is **never dispatched again**. Asserted with a deliberately poisonous unit: the job reaches completion, the poison is one quarantined register entry, and it is not retried past the bound.
6. **AC6 — Memory is bounded per unit; an oversized unit is `resource-exhausted`, not an outage (AD-17).** No single **top-level** *pièce*, however large, is required to fit in memory whole; a unit exceeding its **configured** `import_unit_max_bytes` enters the register as `resource-exhausted` and the worker survives and continues. Capacity bounds are *configuration-as-data* with defined defaults (the `backup_interval_hours` `valid=` pattern). *(Amended per the review: the config bound covers top-level submitted units; a container's members are read by the pre-existing `ZipExpander` under its own hard-coded ceiling — wiring the config bound through to archive members is Story 2.4, which owns container expansion.)* Asserted by test: an over-bound unit → `resource-exhausted` register entry, worker alive, job completes.
7. **AC7 — The queue is sealed behind one submodule (AD-17 structural property).** No module outside `apx/adapters/store_postgres/queue` (the new submodule) may import or query a Procrastinate/queue table. Asserted by a **static check registered in the AD-33 harness**, with a failure-path fixture (a runtime module that touches the queue table fails the build), fail-closed on unparseable.
8. **AC8 — Submission is idempotent; one open *import job* (AD-6, FR-7).** A repeated submit (double-click, retried fetch, SPA remount) does **not** create two jobs or double-count — enforced by a client-supplied idempotency key and/or Procrastinate `queueing_lock`, plus the FR-7 **one-open-import-job** rule (a second submit while one is open for the *matter* returns the existing job, never a second). Asserted by test.
9. **AC9 — The *submitted* set is frozen at enumeration-and-expansion completion, and the enumeration is recorded (AD-17); provisional until then.** The ledger's *submitted* is provisional while enumeration runs and freezes at its completion; the enumeration (the unit list) is recorded so resume knows the whole set. Asserted by test.
10. **AC10 — Honest boundaries, green, and the entrypoint test updated.** No extraction/OCR (2.3), container-expansion (2.4), identity (2.5), register-UI/bulk-retry (2.6), completion-summary (2.10), worklist (2.11), or durable-exclusions (2.7) work is built. `tests/checks/test_entrypoints.py` (which today asserts **zero** apx tasks) is updated to expect the one ingestion task. The `save`/audit path is preserved for existing callers. `ruff`, `python -m apx.checks` (now incl. the queue-seal check), `pytest` (incl. the Postgres-leg resume test where a DB is available), `tsc`, and the offline fitness function are green; the payload build gate is untouched.

## Dev Notes

- **AD-17 is the contract; its two subtle mechanics are the ones that fail if rushed.** (1) **The attempt counter is incremented in a transaction committed *before* the unit's work begins**, so an OS-level kill still advances it — otherwise a `SIGKILL` mid-unit leaves the counter untouched and resume loops onto the poison forever. (2) **The quarantine transition and its *failure register* entry are committed in a transaction *independent* of the failing unit's** — an exception handler that writes inside the failing transaction rolls back with it, and the poison is retried forever. Both are quoted verbatim in AD-17. [Source: ARCHITECTURE-SPINE.md#AD-17 lines 507-524]
- **The application-owned ledger — not Procrastinate's job table — is the single authority** for unit state and for every user-visible progress figure. "No module outside `adapters/store_postgres/queue` may query a queue table" is a *structural property* (AC7). Procrastinate's table is cheaper to query, which is exactly why two readers would otherwise disagree on "processed against submitted" during retries and after quarantine. Read progress from the ledger. [Source: ARCHITECTURE-SPINE.md#AD-17 lines 507-513]
- **AD-6: the HTTP request never does work.** Today `ingest_upload` (`apx/api/app.py:907-964`) runs `ingest_folder` + `_persist` *in-request* — the exact v1 defect AD-6 names ("one synchronous function … accumulating every point in memory before a single write … cannot ingest 1 700 *pièces*, let alone 100 000"). 2.2 makes it validate → durably record → enqueue → return. Progress advances only by a worker committing a unit. [Source: ARCHITECTURE-SPINE.md#AD-6 lines 203-224; apx/api/app.py:907-964]
- **`ingest_folder` is all-or-nothing in memory today — this is the hard refactor.** `apx/core/app/ingest.py:90-169` mutates one `IngestionResult` and returns it whole; every `IngestedPiece.full_text` is resident simultaneously (`ingest.py:143-157`). 2.2 must let the worker **stream and commit units one at a time** (enumerate first — AC9 — then per-unit extract+commit) so no *pièce* need fit in memory whole (AC6). Reuse the classification logic; do not rewrite the extractor/expander. [Source: apx/core/app/ingest.py:90-169]
- **`store.save` is already idempotent — lean on it, but rework the per-call audit.** Deterministic ids + `session.merge` in one transaction make a re-run a no-op upsert (`store.py:500-524`; `Piece.id = piece_id(tenant, content_hash, matter)`, unique `(tenant,matter,content_hash)`). BUT `save` writes **one `ingest` audit entry per call** with the whole-result inventory (`store.py:499`). A naive per-unit commit would write 100 000 audit entries. **Recommended:** one `ingest` audit entry per *job* (recorded once, e.g. at completion with the frozen counts, or at enqueue), and the per-unit commits update the ledger only — matching AD-6 "the idempotency key of a unit covers its audit entry; a re-executed no-op writes no new entry." Confirm in Open Question 3. [Source: apx/adapters/store_postgres/store.py:447-524; ARCHITECTURE-SPINE.md#AD-6 lines 214-219]
- **The worker needs the same DB as the store.** Build the connector from the same `DATABASE_URL` via the queue submodule; `engine.make_session_factory()` / `database_url()` (`apx/adapters/store_postgres/engine.py:42-53`) is the pattern. AD-5 asserts at start-up that the queue, vector store and ledgers resolve to the same endpoint. [Source: apx/adapters/store_postgres/engine.py; ARCHITECTURE-SPINE.md#AD-5 lines 187-194]
- **Procrastinate 3.9 primitives (installed, currently unused):** `PsycopgConnector`/`SyncPsycopgConnector` (real DB); `testing.InMemoryConnector` (tests — supports `App.run_worker(wait=False, listen_notify=False, install_signal_handlers=False)` to drain synchronously + `connector.jobs`/`finished_jobs` to inspect); `RetryStrategy(max_attempts=…)` → `get_retry_decision` returns `None` past the bound (the quarantine hook); `queueing_lock` on a task/defer (idempotent submission).
