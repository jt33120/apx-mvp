# Story 1.12: The structural-properties harness

Status: review

## Story

As the APX build standing in for the engineers who are not on the team,
I want every "no code path does X" claim in the PRD backed by a **named static check in CI**, and the set of properties itself made a checked object,
So that a guarantee is decided by a machine, not by a human remembering to look — and a property silently dropped fails the build.

**Scope in one line:** promote the ad-hoc `apx/checks/` list into a **harness with a manifest** — a single enumerated registry of structural properties, each naming its FR, its governing AD, the **check that enforces it** and the **file or pattern it inspects** (AD-33) — and make the manifest *itself* a structural property: **a listed property whose check is missing, unregistered or unresolvable fails the build**, and a registered check absent from the manifest fails the build (the two directions lock the manifest to the runner, the way the config-keys pair locks docs to schema). Add the **missing checks** from FR-56's enumerated floor of 13 so every one is a *live, fixture-proven* check — several are *forward-looking* (their subject arrives in a later epic; the check scans the relevant surface, passes vacuously today, and fires the day the code lands, exactly as the egress guard is green on the empty tree). Honour the **three verbs** mechanically: *asserted by test* / *enforced as a structural property* / *asserted by review* — a review-verb or test-verb row is tracked but is **never counted as a structural check**, and the fourth label `[NOT ENFORCEABLE]` is representable. **Not** the FR-21 user-reachable-actions registry (a later usability-probe story), **not** the i18n string sets / retrieval / embedder / confidence code the forward-looking checks will one day guard (their stories own them), **not** new runtime behaviour of any kind — this story ships checks and a manifest, nothing the product does at run time.

> This is the story that makes "the tests stand in for the engineers we do not have" honest. Its own most dangerous failure is an *inflated claim about what the suite proves* (AD-33) — so the deliverable is not "more green checks" but a manifest that makes the **absence** of a check loud, and a discipline that never lets a human-judged sentence masquerade as a machine-decided one.

## Acceptance Criteria

> **Given** the set of structural properties the PRD enumerates, **When** the harness runs, **Then** each named property has a check — grep, lint, import-graph or architecture rule — that fails the build on violation, and **a property with no check is itself a build failure** (FR-56).
> **And** the set includes at minimum: no fallback embedder (FR-9), destructive index operations reachable from one entry point only (FR-10), no post-filter in retrieval (FR-14), one *chunk* write boundary with a required scope argument (FR-8), no *tenant*-specific identifier in source (FR-30), no runtime import from the test tree and no fixture path (FR-33), no natural-language string as a translation key (FR-34), no hard-coded locale (FR-35), no outbound call site outside the enumerated adapters (FR-32), no reversible credential storage (FR-48), no secret in source (FR-51), no model-reported confidence field consumed (FR-42), and no banned *confidence bound* phrasing in any locale (FR-23).
> **And** each property names the check that enforces it and the file or pattern it inspects.
> **And** where a claim cannot be decided by a check or a test, the document's verb is honoured — *asserted by test*, *enforced as a structural property*, or *asserted by review* — and the third is never counted as a passing test (FR-56).

1. **AC1 — The manifest, and it is itself checked (AD-33/FR-56).** A single **property manifest** (`apx/checks/manifest.py`) enumerates every structural property as a row carrying: the FR, the governing AD, a short name, the **verb** (`structural` | `test` | `review` | `not-enforceable`), the **check** it names (a dotted `module.function` for a `structural` row, else none), and the **file/pattern it inspects**. Two meta-checks make the manifest a build gate: **(a)** every `structural` row names a check that resolves to a callable **registered in the runner** (`apx/checks/__main__.py::CHECKS`) — a missing, unresolvable or unregistered check fails the build (*a property with no check is not a property*); **(b)** every callable registered in the runner appears as some manifest row's check — an orphan/untracked check fails the build. Both fail closed.
2. **AC2 — The enumerated floor of 13 all have live, fixture-proven checks (FR-56).** Each of the 13 properties in FR-56's list is present as a live check in the runner and named by a manifest row. The ones whose subject exists now are real checks over the real tree (FR-8, FR-30, FR-32, FR-33, FR-48, FR-51); the ones whose subject is a later epic (FR-9 embedder/2.8, FR-10 index/2.8, FR-14 retrieval/3.x, FR-34/FR-35 i18n/6.x, FR-42/FR-23 confidence/4–5) are **forward-looking**: the check scans the relevant surface, passes vacuously today, and each carries a **failure-path fixture under `tests/_fixtures/`** proving it fires on the violation it will one day meet. No check passes vacuously *without* a fixture that fires.
3. **AC3 — Each property names its check and the pattern it inspects (AD-33).** Every manifest row's `inspects` field names the concrete file, directory or pattern the check reads (e.g. "`apx/adapters/**` import graph + socket call sites", "`t(...)`/`gettext(...)` call args"), and this is surfaced both in the manifest and in a **README structural-properties reference block** (`<!-- structural-properties:start/end -->`), kept in lock-step with the manifest by a meta-check in both directions (mirroring the config-keys pair) — a shipped-README block that drifts from the manifest, or is removed, fails the build.
4. **AC4 — The three verbs, made mechanical (AD-33/NFR-51).** The manifest represents all four verbs; a `test` or `review` (or `not-enforceable`) row **must not** name a structural check and **must not** appear in the runner — a review-asserted claim is tracked as documentation but is *never counted as a passing structural check*. A meta-check enforces this partition (a `structural` row must name a registered check; a non-structural row must not), so "the third is never counted as a passing test" is decided by a machine, not by care.
5. **AC5 — Honest boundaries, named.** The forward-looking checks state, in their docstring and manifest `inspects`, that they are vacuously green until their subject lands (which story), so a reader does not mistake "green" for "guarding live code today". The FR-21 user-reachable-actions registry (AD-33's other "registry is a property" clause) is **named as deferred** to its usability-probe story, not silently absent. The `[NOT ENFORCEABLE]` clauses AD-33 itself lists (AD-3, AD-19, AD-15's rejection record, AD-27) are representable as manifest rows so the harness can account for them without counting them as checks.
6. **AC6 — Green and honest.** All existing tests pass; `ruff` + `python -m apx.checks` + `pytest` + fitness green; the runner still prints one line per check with its name and AD; README documents the harness and carries the reference block; no over-build (no FR-21 registry, no i18n/retrieval/embedder/confidence runtime code, no new product behaviour).

- **The forward-looking idiom is the `scope_admin` pattern, and it is honest, not a stub.** `scope_admin.scope_mutations_are_audited` shows it: on the real tree assert the expected shape (and pass when nothing violates), and accept an injected `roots` fixture that violates so the fixer proves the check *fires*. A forward-looking check (no embedder yet, no retrieval yet) scans the surface its subject will occupy, returns green because there is nothing to catch **yet**, and its fixture demonstrates the catch. This is exactly how the egress check is green on the empty tree. The manifest `inspects` and the docstring MUST say "vacuous until story X" so green is not mistaken for live cover (AC5). A vacuous check with **no firing fixture** is the anti-pattern this story exists to prevent — do not add one. [Source: apx/checks/scope_admin.py]
- **The shared AST toolkit — reuse it.** `from apx.checks.payload_schema import _load_trees, _fail_closed, _is_call_to, _iter_py, _parent_map, _enclosing_func, _param_has_default`. `_load_trees(roots)` returns `(trees, unparseable)`; a non-empty `unparseable` MUST short-circuit to `_fail_closed(...)` (a file you cannot parse is a failure, never a silent skip). Text-scanning checks follow `secrets.py`: exclude `web`, `node_modules`, `.venv`, `.git`, `_bmad`, `_bmad-output`, `.claude`, and `_fixtures`. [Source: apx/checks/payload_schema.py, secrets.py]
- **The three verbs, made mechanical (AD-33/NFR-51).** AD-33 uses four labels: *asserted by test*, *enforced as a structural property*, *asserted by review*, and `[NOT ENFORCEABLE]` (naming what stands in its place). This makes "the third is never counted as a passing test" a machine decision. AD-33 lists its own `[NOT ENFORCEABLE]` clauses — AD-3 (deny-list stands in), AD-19 ("plausible-looking"), AD-15's rejection record, AD-27's commercial statement — represent these as `not-enforceable` rows so the harness accounts for them. Seed the check's banned-phrase list with that literal (case-insensitive, whitespace-tolerant) plus the obvious shapes ("probability nothing was missed", "chance nothing relevant was missed"), scan any locale/string resources and source strings, and note that the full multi-locale list grows as the string sets do (5.4/6.x).
