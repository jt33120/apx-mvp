## Story

As a lawyer who knows what she is trying to establish,
I want to state it in my own words at any time and have the ranking be relative to it,
so that relevance is a relation to my question, not a property the tool guessed at.

## Scope note — BACKEND foundation (the versioned, audited, referenceable case theory), ranking machinery deferred

The **first story of Epic 4**, and the only irreversible-ish data decision the epic rests on before ranking exists: **what a *case theory* IS as stored data** — a matter's optional free-text statement of what the lawyer is trying to establish, versioned append-only, every write recorded in the *audit record*, each version carrying a **stable identity a future *ranking version* will name** (AD-23). Epic 4's whole "relevance is a relation to a question" premise (FR-37, §0 of the PRD) begins here.

**What exists today (verified first-hand):** `case_theory` is a **single current-value, encrypted column on `matter_scope`** ([models.py:281-283](../../apx/adapters/store_postgres/models.py#L281-L283)), with the comment *"A single current value here; the versioned/audited/re-rankable model is Epic 4 (story 4.1), which supersedes this column."* Its write path ([store.py:660-663](../../apx/adapters/store_postgres/store.py#L660-L663)): a restated theory **updates in place**, a skipped one never wipes an existing one, *"Versioning is Epic 4."* It is threaded from the import screen (`IngestRequest.case_theory` → `save(..., case_theory=...)`) and staged on `import_job.case_theory`. **This story builds the versioning that column comment promises.**

**What this story builds (backend, fully pytest-verifiable — no frontend harness ships, AD-29):**

- **A new append-only entity `case_theory_version`** — one row per version of one matter's case theory, keyed `(tenant, matter, version_no)`, the text `EncryptedText` (AD-31: confidential legal strategy, never a query key), a **withdrawal** encoded as a version with `NULL` text (a "delete" that is append-only — AC4 / FR-37, never a hard delete, AD-7). A deterministic `id = sha256(tenant \0 matter \0 version_no \0 text)` — the **referent a future ranking version names** (AD-23 records "case theory version"). FK `(tenant, matter)` → `matter_scope` with **no cascade** (AD-7). Migration `0023_case_theory_version` chained from the current head `0022_deterministic_index`, with a **backfill** seeding version 1 from any existing `matter_scope.case_theory` value.
- **One owning use case** (`SqlStore.append_case_theory_version`) — AD-37 "one owning use case per transition." It reads the current max `version_no` + current active text **in one transaction**, is a **no-op on unchanged text** (idempotent re-import, mirroring config no-op — no version, no audit), else inserts `version_no = max+1`, updates the denormalised `matter_scope.case_theory`, and writes **one `_append_audit` entry** (`case_theory_written` / `case_theory_withdrawn`) — **atomic with the version** (AD-22). A `(tenant, matter, version_no)` unique constraint makes a concurrent double-write **fail loudly**, never silently overwrite (AD-37 conditional commit).
- **Scoped, non-disclosing reads** — `read_case_theory` (the current active version, or absent/withdrawn) and `list_case_theory_versions` (the full readable history, FR-37 "retains previous versions readably"), each **scope pre-filtered** (AD-13): an out-of-scope or absent matter is indistinguishable → the same non-disclosing 404 (FR-14).
- **Four API endpoints** — `GET /api/matters/{matter}/case-theory` (current), `PUT …` (write/rewrite → new version), `DELETE …` (withdraw → withdrawal version), `GET …/case-theory/versions` (history). Writes are wall-gated (`scope ∈ ident.scopes`) and **audited**; reads are scope-gated and **not** audited (consistent with the audit-trail read and config reads — ratified assumption below).
- **The import path routes through the owning use case** — `save(..., case_theory=...)` stops writing the column directly and calls `append_case_theory_version` in the ingest transaction, so an **import-time** theory is versioned and audited from version 1 (FR-37 "writable at import").
- **A new structural gate** `case_theory_version_is_append_only` (AD-33, mirroring `register_ownership`) — the version table is written **only** from the owning module and is **never `UPDATE`d or `DELETE`d** anywhere (append-only is a *structural property*, not a promise — Epic 4's ethos, AD-7). Registered + manifest + README in lockstep.

**What is deferred (honestly — the ranking half of the ACs; this story delivers its precondition, not a stub of it):**
- **Ranking, the *ranking version*, the re-rank act (FR-38/FR-39)** — Stories 4.2/4.3. They do not exist yet. AC2's *"offers a re-rank"* and AC3's *"a re-rank produces a new ranking version; human-set values / pins / validation acts survive marked as human-set"* need a ranker, `ranking_version`, `pins` (4.11) and `validation acts` (Epic 5) — **none exist**. This story delivers the two halves it CAN: **(a) the "never automatic" guarantee** — a case-theory write triggers **no** recompute of anything (tested: a write's only effects are the version row + its audit entry), and **(b) the referenceable version identity** a future ranking version will bind to (AD-23). The **"offers"** half (a worklist line / a re-rank button) waits for ranking (4.3) **and** the *worklist* (FR-27, backlog 2-10/2-11).
- **The dedicated frontend surface** (a matter's case-theory write/history panel) — no UX contract is flagged for 4.1, and the *matters zone* (Story 2-11) is backlog. The **existing import field** already threads the theory into the now-versioned path; a bespoke UI lands with the matters zone or a thin follow-on. The API defined here is the contract that UI will consume. (Verified: `apx/web` has **no** test harness — AD-29 ships no Node runtime — so a UI here would be unverifiable beyond `tsc`; the backend is where the guarantees are testable.)
- **`matter_scope.case_theory` is retained** as a **denormalised current-value cache** (like `submitted_pieces` on the same table), NOT dropped — the version table is the source of truth. Dropping the column would touch `backfill.py`'s re-key machinery, `admission.py`, the encryption allowlist and `import_job` for marginal benefit; retaining it keeps the system working end-to-end. A consistency test asserts the cache equals the latest version's text (NULL when withdrawn).

## Acceptance Criteria

1. **A case theory is free text in her own language, optional at import and writable at any later moment, never mandatory; its absence never blocks ingestion, ranking or anything else (FR-37, FR-1).** The `PUT /api/matters/{matter}/case-theory` endpoint accepts free text at any time; the import path (`IngestRequest.case_theory`) still accepts it at onboarding; **no path is made mandatory** and a matter with no case theory ingests, is read and (later) ranks exactly as before. *(tests: ingesting a matter with no case theory succeeds and `read_case_theory` returns absent; writing one later succeeds; the import-time and later-write paths both produce version rows; an out-of-scope matter's theory is non-disclosing 404 on read and write.)*

2. **Writing or rewriting produces a new version, retains previous versions readably, is recorded in the audit record with actor and timestamp, and the re-rank is explicit and never automatic (FR-37).** Each distinct write appends a `case_theory_version` (`version_no` = previous + 1); `list_case_theory_versions` returns **all** prior versions readably in order; each write writes **exactly one** `_append_audit` entry (`case_theory_written` / `case_theory_withdrawn`) carrying the actor and the wall-clock timestamp, **atomic** with the version (both commit or neither, AD-22). A write whose text equals the current active text is an **idempotent no-op** (no version, no audit). **No write triggers any recompute** — a case-theory write's only effects are the version row, the denormalised cache update and the one audit entry (the "never automatic" guarantee; the "offer a re-rank" surface is deferred with ranking). *(tests: two distinct writes yield versions 1 and 2, both readable; each writes one audit entry with actor+timestamp on the tenant chain; an idempotent rewrite writes neither; a write creates no ranking/other artefact.)*

3. **Deletion is append-only — deleting a case theory does not delete prior versions (nor, once they exist, the rankings computed under them), which remain readable bound to the version that produced them (FR-37 failure path, AD-7).** `DELETE /api/matters/{matter}/case-theory` appends a **withdrawal** version (`NULL` text), audited as `case_theory_withdrawn`; **every prior version row is untouched and still returned** by `list_case_theory_versions`; `read_case_theory` then reports the theory as withdrawn/absent while the history remains. A structural check asserts the table is **append-only** — written only by the owning module, never `UPDATE`d or `DELETE`d. *(tests: writing then withdrawing leaves versions 1..N present and readable, N+1 the withdrawal; the current read is withdrawn; the gate fires on a fixture that UPDATEs/DELETEs the version table and on a write from outside the owning module; passes the real tree.)*

4. **Each version carries a stable identity, and the whole entity honours tenant isolation and encryption at rest (AD-23, AD-31, AD-12, AD-7).** A version's `id` is the deterministic `sha256(tenant \0 matter \0 version_no \0 text)` — stable and collision-free (a future *ranking version* names it, AD-23); `text` and `actor` are `EncryptedText` (AD-31 — the encryption structural check passes for the new columns); `tenant` is non-null (AD-12 tenant-isolation checks pass); the FK carries **no cascade** (AD-7). Re-running the migration's upgrade→downgrade→upgrade under SQLite CI is clean, and the backfill seeds an existing column value as version 1 under a `system:` actor. *(tests: the id is deterministic and stable across two computations; `python -m apx.checks` stays green including the encryption + tenant-isolation + no-cascade checks; the migration round-trips; the backfill produces version 1 for a pre-existing theory and none for an absent one.)*

## Dev Notes

### The one irreversible-ish decision: what a case theory IS as stored data

Epic 4 is "relevance is a relation to a question." The question is the *case theory*. Story 4.1 fixes its **storage identity** before any ranking binds to it — so a later *ranking version* can name a *case theory version* (AD-23) that is **stable, referenceable and never mutated**. Get the shape right here; it is the hinge the rest of Epic 4 hangs on.

- **The ER model already names it**: `MATTER ||--o{ CASE_THEORY_VERSION : "versions"` ([ARCHITECTURE-SPINE.md:1534](../../_bmad-output/planning-artifacts/architecture/architecture-apx-mvp-2026-07-21/ARCHITECTURE-SPINE.md#L1534)). This story realises that entity.
- **FR-37 is the contract** ([prd.md:791-801](../../_bmad-output/planning-artifacts/prds/prd-apx-mvp-2026-07-20/prd.md#L791-L801)): free text in her language; optional at import (FR-1) and writable/rewritable/**deletable** at any later moment; never mandatory; **every rewrite is a new version, previous versions retained readably, recorded in the audit record with actor+timestamp**; the re-rank is **user-initiated and explicit, never automatic** (an automatic re-rank would overwrite the work FR-20 protects); and every derived artefact names the case theory version it used **or names that none existed**.

### There is no `Matter` table — key on `(tenant, matter)`

A "matter" is the composite string PK `(tenant, matter)` on **`matter_scope`** ([models.py:254-283](../../apx/adapters/store_postgres/models.py#L254-L283)) — **no UUID**, no separate timestamps. `case_theory_version` therefore keys on `(tenant, matter)` + a `version_no`, FK to `matter_scope` (no cascade, AD-7). Scope is resolved from `matter_scope` **at query time** and pre-filters every read (AD-13) — **never denormalised onto rows**; do the same for case-theory reads (mirror `read_piece` at [store.py](../../apx/adapters/store_postgres/store.py), `read_audit`).

### The audit-write path — reuse it verbatim, atomic with the version (AD-22)

`SqlStore._append_audit(session, tenant, matter, actor, action, detail, ts)` ([store.py:595-614](../../apx/adapters/store_postgres/store.py#L595-L614)) appends **inside the caller's transaction** — a per-tenant monotonic `seq`, a sha256 hash chain over the previous entry, and (via `before_flush`/`after_commit` listeners) a head-journal write outside the restorable DB. **Call it in the same `session.begin()` as the version insert** so the two are atomic (an action whose audit entry cannot be written **fails** — AD-22). The `action` is a plaintext categorical verb (existing verbs: `ingest`, `open-piece`, `config_changed`, `judge`, …); use `case_theory_written` / `case_theory_withdrawn`. The `detail` is `EncryptedText` — put `version={n}` (a reference), **not** the theory text itself (the text lives, encrypted, in the version row; do not duplicate confidential content into `detail`). Actor = `ident.actor` for user writes; `system:backfill` for the migration seed (the `system:`-prefix convention for non-user principals — AD-48/AD-26 — is a naming convention on the string, there is **no** principal-type enum).

### AD-49 / the clock — you need no new `Clock` port

There is **no `Clock` port** in the codebase; wall-clock is `datetime.now(UTC)` captured at the call site and passed as `ts`. The **monotonic** ordering AD-49 wants is already carried two ways: the audit entry's per-tenant `seq`, and the case theory's own `version_no` (1,2,3… per matter). The version row stores `created_at` (wall-clock) for human reading; ordering and "which is current" use `version_no`. Do not invent a clock abstraction.

### The closest analogs to mirror

- **Append-only + monotonic + "correction is a new entry, never edit/delete"** — `AuditRecord` ([models.py:341-369](../../apx/adapters/store_postgres/models.py#L341-L369)). This is exactly the discipline FR-37 wants for versions.
- **A child table keyed to a parent, deterministic sha256 `id` PK, encrypted content column, FK with no cascade** — `PieceProvenance` / `PieceCustodian` ([models.py:108-143](../../apx/adapters/store_postgres/models.py#L108-L143), migration `0018`). Structural template for the new table.
- **"One owning use case per transition," enforced statically** — `register_ownership.py::register_state_written_once` ([apx/checks/register_ownership.py](../../apx/checks/register_ownership.py)) fails the build if `Failure.resolution_state` is written outside `adapters/store_postgres/`. Task 5's gate mirrors it for the append-only version table.

### Encryption + tenant-isolation structural checks WILL bind the new table

`checks/encryption.py::sensitive_columns_are_encrypted` (AD-31) requires **every** `Mapped[str]` column to be `EncryptedText` unless allowlisted — so `text` and `actor` **must** be `EncryptedText`; `tenant`/`matter`/`version_no`/`created_at` are not `str` content and are fine plaintext (structural metadata / query surface, like `audit_record.seq`/`chain`/`timestamp`). Do **not** add the new columns to the plaintext allowlist ([checks/encryption.py:63-74](../../apx/checks/encryption.py#L63-L74)). `tenant_isolation.*` (AD-12) requires `tenant` non-null on owned tables and tenant-qualified identity — satisfied. `payload_schema.no_cascade_delete` (AD-7) requires the FK carry no `ondelete` — satisfied.

### The ranking half is genuinely out of scope — deliver the precondition, not a stub

Ranking (`ranking_version`, FR-38/FR-39), **pins** (4.11), **validation acts** (Epic 5) do **not** exist. So:
- **"offers a re-rank that is explicit and never automatic" (AC2/FR-37)** — deliver the **"never automatic"** half now (a write triggers **no** recompute — tested by asserting a write's only effects are the version row + denormalised cache + one audit entry, and that no ranking/other artefact is created). The **"offers"** half (a worklist line / re-rank button) needs ranking (4.3) **and** the *worklist* (FR-27, backlog) — deferred.
- **"a re-rank produces a new ranking version; human-set values / validation acts / pins survive marked as human-set" (AC3)** — entirely a **4.2/4.3/4.11/Epic-5** concern. This story delivers its foundation: a **stable, referenceable `case_theory_version.id`** (a future ranking version names it, AD-23) and an **append-only history** (a new/withdrawal version never mutates or deletes a prior one, so anything a future ranking binds to a prior version stays readable — AC4/AC3 semantics that reduce, today, to "prior versions remain readable after a withdrawal").
- **Do NOT** build a ranker, a `ranking_version` table, pins, validation acts, or a re-rank endpoint in this story. Building them here is the classic over-build; the ACs' ranking clauses are satisfied by the precondition + the "never automatic" guarantee, and named explicitly as deferred in the completion notes.

### Ratified assumptions (Julian's delegate — fast path)

1. **Retain `matter_scope.case_theory` as a denormalised current-value cache**, version table authoritative — NOT a full column drop (surgical; keeps `backfill.py` re-key, `admission.py`, the encryption allowlist and `import_job` working). A consistency test asserts cache == latest active version text.
2. **Reads are not audited**; writes are (FR-37 mandates write audit; reads mirror the un-audited `read_audit`/config-read pattern). Revisit if the case theory is later deemed to require read-audit like pièce content (FR-45) — a one-line addition then.
3. **A withdrawal is a NULL-text version** (append-only "delete"), not a separate `withdrawn` boolean — one mechanism, unambiguous, and symmetric with the existing `save` normalisation `"" → None`.
4. **Import-time theory is versioned from version 1** by routing `save` through the owning use case — so *every* case theory version (including the onboarding one) is audited, per FR-37.

Instead, **`save` is left UNTOUCHED** (its heavy existing test suite is unaffected) and the versioned+audited write is called at the **API import boundaries** — inside `_persist` after `admit` (sync `/api/ingest`) and after the matter-creating save in `/api/ingest-upload`. Writing at the API boundary versions the theory at the moment the user states it (upload/ingest time), on both paths, atomically with its own audit entry. `matter_scope.case_theory` is reconciled by the owning method (and still set by `save`, same value in-request — harmless); the version table is the source of truth.
