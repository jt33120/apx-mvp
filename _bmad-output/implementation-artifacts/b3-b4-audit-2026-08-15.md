# B3 + B4 — the decision–implementation audit and the requirements sweep

**Date:** 2026-08-15 · **Action items:** B3 (every `[ADOPTED]` AD implemented at a named site or
deferred with an owner) and B4 (the same, clause by clause, for the 60 FRs) · **Method:** 26
adversarial agents in two fan-outs, every verdict adjudicated by an independent skeptic ·
**Coverage: 49/49 decisions, 60/60 requirements, 0 chunks lost, 0 unadjudicated.**

---

## 1. Read the method before the numbers

**The verdict labels are biased, deliberately and by my instruction.** Both auditors were told to
*"prefer the harsher verdict when uncertain"* and to *"err toward splitting"* a rule into clauses.
That is the right bias for finding what an audit exists to find, and it makes the headline tallies —
37 of 49 decisions `partial`, 55 of 60 requirements `partially_built` — **useless as a score**. A
decision with nine clauses of which one is unguarded scores `partial`, and so does one that is
broken.

So this document does not report a score. It reports **what was verified**, and it separates three
things the tallies conflate: a clause that is *unbuilt and recorded* (fine — that is a plan), a
clause that is *unbuilt and unrecorded* (the thing B3 was commissioned to find), and a clause that is
*contradicted by shipped code* (rare, and severe).

**Everything in §3 I re-verified myself**, by running code or reading the cited lines, after the
agents reported it. Two agent claims did not survive that check and are corrected in §5. The
project's own retrospective says not to take a subagent's word at face value; §5 is what happens when
you don't.

| | B3 (decisions) | B4 (requirements) |
|---|---|---|
| Scope | 49 ADs | 60 FRs |
| Auditors + skeptics | 7 + 7 | 6 + 6 |
| Chunks lost | **0** | **0** |
| Unadjudicated | **0** | **0** |
| Verdicts overturned by the skeptic | **13** | **27** |
| Direction of every overturn | toward the harsher reading | toward the harsher reading |
| Clauses recorded as not built | — | **141** |

**Every one of the 40 overturns moved toward the harsher verdict.** No skeptic rescued an auditor's
verdict from being too severe. Either both passes share a bias I introduced, or the auditors were
systematically generous. The honest reading is: some of both, and it is why §3 exists.

## 3. The seven findings I verified personally

### 3.1 `POST /api/ingest` reads any directory the server can reach — HIGH, security

```python
folder = Path(req.folder)                                   # apx/api/app.py:1347
if not folder.is_dir():
    raise HTTPException(status_code=400, detail=f"not a folder: {req.folder}")
```

`IngestRequest.folder` is a bare `str` off the request body (`app.py:383`). There is **no root, no
containment check, no allowlist** — `folder.is_dir()` is the entire validation. Any authenticated
user, holding any scope, can name any directory the API process can read and have it walked
(`rglob`), extracted, persisted into *their own matter under their own RBAC scope*, and its originals
retained for later viewing.

That reads across every wall in one request: another *matter*'s retained originals, another
*tenant*'s spool, anything else on the host. The product's stated non-negotiables are *RBAC by matter
(Chinese walls)* and *tenant isolation*; this route is under both of them.

**It is not unreachable.** The SPA uses `/api/ingest-upload`, but `/api/ingest` is registered as a
live production action (`ingest-folder-route`, `apx/checks/user_actions.py:200`) and answers any
authenticated caller.

**And the class was already known.** Story 2.1's review found and fixed a path traversal on the
*upload* path — *"a crafted `../../` filename escaped the temp sandbox"* — and never asked the same
question of the sibling route that accepts an absolute path outright. FR-1's own PRD section calls
this gesture *"the widest attack surface the product has"*, and lists among its testable
consequences *"traversal is confined to the selected subtree"*, *"a link pointing outside the subtree
is recorded in the failure register with class `traversal-outside-root`"*, and *"traversal cycles are
detected"*. **None of the three is built.**

### 3.2 Nine tenant-scoped tables are absent from the backup — HIGH

Derived by me from the live model metadata, not from a reading:

```
mapped tables: 35   tenant-scoped: 29   in _BACKUP_TABLES: 20

artefact_stamp · case_theory_version · import_job · piece_open · ranked_entry ·
ranking_version · register_override · sampling_run · validation_act
```

A restore from a backup taken today loses **every ranking version and ranked order, every case
theory, every sampling run and therefore every confidence bound, every validation act, every recorded
*pièce* open, every register override, and every freshness stamp.** The *audit record* survives — so
the restored record would attest that a lawyer validated a *pièce* while the ledger proving it is
gone.

`_BACKUP_TABLES` is a hand-maintained tuple. Story 5.5 found `audit_chain_head` missing from it and
added that one table. Story 5.9 added `journal_gap`. Story 5.6's re-review (B2) independently found
`register_override` missing. **Nobody ever asked whether the list was complete, and no check asserts
it** — while `tests/probe/test_never_hard_delete.py` protects a *new* table by default, precisely the
discipline this list lacks.

### 3.3 AD-32's first named item is not in the backup at all — HIGH

AD-32's Rule opens: *"a complete restorable backup of a tenant — **originals**, extracted text,
index, audit record, failure register, configuration"*. `backup_tenant` (`store.py:3187`) executes
`SELECT * FROM {tbl} WHERE tenant = :t` over `_BACKUP_TABLES` and nothing else; the string
`original` does not appear in the function. The retained originals live on the filesystem under
`FilesystemOriginalStore`. The backup is also written as **plaintext JSON** (`apx/manage.py:123`).

### 3.4 The ranking act has no production caller — HIGH, and it is two epics deep

```
$ grep -rn "produce_ranking|record_ranking|run_cascade" --include=*.py apx/
  → definitions only. apx/api/app.py: 0 matches.
$ grep -rl "produce_ranking" tests/ | wc -l
  → 8
```

No HTTP route, no worker job and no `manage` command creates a *ranking version*. The only judgement
a user can invoke is `POST /api/matters/{matter}/judge`, which runs `triage_pieces` — the Story-2.x
label pile — not the Epic-4 cascade.

**This one is recorded**, and the agent's claim that it was not is corrected in §5. Story 4.6 states
it plainly: *"`produce_ranking` has no production caller yet, a documented deferral"*, and Story 4.13
repeats it. The finding is therefore not a hidden defect but something arguably worse:

> Everything Epics 4 and 5 built — the ranked table, **the line**, pins, the priced move, derived
> confidence, justifications, the sampling run, the estimator, the bound, the validation act, and
> §5–§9 of the *matter record* — stands on an act that no user gesture can perform. **22 stories, and
> `epics.md` schedules the wiring in none of them.** Epic 6 is the last epic in the plan and does not
> contain it.

### 3.5 AD-4's two tightening contracts were commented out and never restored — verified

```toml
# [[tool.importlinter.contracts]]  # tightened in 1.12
# name = "no adapter imports another adapter (AD-4)"
# type = "independence"
```

Both are labelled *"tightened in 1.12"*. **Story 1.12 is done.** My own AST walk of `apx/adapters`
finds **13 cross-package import edges across 8 distinct package pairs** (`store_postgres →`
embedder_bgem3, expansion, extraction, ocr_tesseract, originals_fs; `render_html →` extraction,
spool; `render_image →` spool). And the commented contract would not restore the property if
uncommented: it names five modules, and an `independence` contract constrains only edges *between
listed* modules, so it would reach **3 of the 8 pairs**.

This is B3's thesis in a single artefact: a deferral, with an owner, whose owner shipped.

### 3.6 `bulk_retry` commits the business acts in N transactions and the audit entry in one more

`store.py:2010-2034`: the `for entry in candidates:` loop opens `with self._sf() as session,
session.begin():` **inside** the loop, and the single `bulk-retry` audit entry is written after it.
AD-22's headline clause is *"an action whose audit entry cannot be written fails. Both happen or
neither does."* Here N business acts commit, and a crash before the final transaction leaves them
recorded nowhere.

This is a **genuine tension between two decisions**, not a simple defect: AD-6/FR-5 require exactly
one entry per bulk job, never one per *pièce*, and the docstring says so deliberately. AD-22 and AD-6
cannot both be satisfied by this shape. **Neither decision records the conflict, and it needs
settling rather than fixing.**

### 3.7 The LLM judge cannot be observed to fail

```python
except Exception:  # noqa: BLE001 — any transport failure degrades safely to UNCERTAIN
    return Verdict(Label.UNCERTAIN, "erreur du juge (indisponible) — à revoir")
```
`apx/adapters/llm_openai_compat/judge.py:80`. AD-19 is *"loud failure everywhere; nothing is
imputed"*. A dead model endpoint yields a verdict, not a failure — and the rationale string does say
so in French, which is why this is medium rather than high. The skeptic's stronger claim, that the
fabricated verdict then produces a *derived confidence with a named observable signal*, is plausible
and **I did not verify it**; it is listed in §6 as work, not as a finding.

## 4. The systematic pattern: the product records correctly and largely does not say so

Of 141 clauses recorded as not built, a large and coherent share are the same sentence:

> *"…and it surfaces on the **worklist** as an actionable line"* · *"…and generates a worklist line"*
> · *"…and an explanatory worklist line"* · *"where an entry is required to be actionable, **the
> action must exist**"* · *"visible, countable, and one click from the list"*

FR-1, FR-2, FR-3, FR-5, FR-6, FR-7, FR-9 and FR-10 each carry one. The mechanism was built every
time; the half that *tells the lawyer and gives her the control* was not. `apx/core/domain/worklist.py`
emits freshness lines and FR-23's unfitness line — and nothing else.

This is one piece of work, not 141 defects, and it is the same shape as §3.4: the substrate is real
and the gesture is missing. **It is also the largest single risk to FR-59, the usability gate**, which
Epic 6 will run against surfaces that do not exist.

## 5. Two agent claims that did not survive verification

Recorded because an audit that never overturns its own agents is not being read.

1. **"AD-18 / the ranking act is unimplemented and nobody recorded it."** The code half is right (§3.4).
   The *unrecorded* half is **false**: Stories 4.6 and 4.13 both state the deferral in writing. The
   finding is real; the framing was wrong, and the wrong framing is the flattering one for the
   auditor.
2. **"AD-39 is violated — a stored, overwritable discarded-set membership ships on a live route."**
   The cited table, `piece_label`, is the Story-2.x *relevance verdict* pile, not the Epic-4 *discarded
   set*. Those are two different artefacts — the exact ambiguity the Epic-4 retrospective §5 was
   written to settle, and the Epic-5 planning review settled by declaring the label pile
   **superseded but readable**. The skeptic reproduced the Epic-4 retro's own confusion. **Not a
   violation of AD-39**; arguably a sign that "superseded but readable" is too subtle to survive.

## 7. What this changes about Epic 6

Epic 6 was to be the last epic: the export, the diagnostic, i18n, locale, the language to the model,
the usability gate. On the evidence above it cannot be, and the honest sequence is:

1. **C1** (the open route) — it is a security defect on a live surface;
2. **C2/C3** (the backup) — a DR guarantee that is false today;
3. **C4** (the ranking wiring) — without it, Epic 6's own Story 6.1 exports a *retained set* derived
   from a ranking no user can produce;
4. **C5** (the worklist half) — before FR-59.

Then Epic 6 as planned. Every one of these is a consequence of the same thing the Epic 5
retrospective named: **a decision, a requirement, a table or a route that was recorded and never
finished reads exactly like one that was.** The instrument B3 asked for now exists; this is its first
run, and it found more than the retrospective predicted.
