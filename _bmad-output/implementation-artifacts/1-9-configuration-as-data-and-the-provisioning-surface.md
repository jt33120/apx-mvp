# Story 1.9: Configuration-as-data and the provisioning surface

Status: review

## Story

As APX operating one codebase for many firms,
I want per-*tenant* behaviour to be data rows edited through one audited surface, and a *tenant* provisioned through it,
So that saying yes to a firm's bespoke need never becomes a per-site code fork — the failure that is fatal at eight clients.

**Scope in one line:** turn per-*tenant* behaviour into **data rows** — a declared configuration schema (`apx/core/domain/config.py`) whose keys (taxonomy, *RBAC scopes*, model provider & endpoint, sources, chunking configuration, exclusion list, cascade & refusal thresholds, interface language) each carry a **default**, edited only through **one audited surface** (`set_config`/`get_config` behind the admin API, every change validated, reversible, and written to the *audit record* with actor/key/before/after); **provision** a *tenant* through it (first administrative grant + scopes + taxonomy in one audited act); and make the guarantees **structural** — three build-failing checks: no conditional under `core/` branches on a *tenant* identifier (AD-24), every documented key exists in the schema, and no default disables the guarantee its key governs (the v1 off-corpus-gate defect, encoded). **Not** the visual SPA (AD-29 — deferred with the rest of the front-end); **not** wiring each threshold into its consumer (each lands in its own epic-2/4/5 story — 1.9 builds the *surface* and the *defaults*).

> The ad-hoc build scattered per-tenant behaviour across environment variables (per-deployment, not per-tenant, changed by a redeploy, audited nowhere) and a single typed `mfa_required` column edited with no audit entry. 1.9 makes "customisation is data, never code" (AD-24) a real mechanism: one key→value store per *tenant*, one audited surface (AD-25), and a build that goes red if a firm's identity leaks into a code branch or a guarantee ships switched off.

## Acceptance Criteria

> **Given** the configuration surface (FR-50), **When** a *tenant* is provisioned, **Then** its first administrative grant is established, and its taxonomy, *RBAC scopes*, model provider and endpoint, sources, chunking configuration, exclusion list, cascade and refusal thresholds, and interface language are all editable as data without a code change or a different deployment (FR-30, FR-50).
> **And** configuration is edited only through that surface — direct database editing is not the mechanism, because it produces no *audit record* entry, no validation and no rollback (FR-30).
> **And** a static check asserts no *tenant*-specific identifier or name appears anywhere in source, and one artefact is built and every installation runs it (FR-30, FR-56).
> **And** every configuration key referenced in any documentation exists in the surface and is asserted to exist by a test; every key has a default, and a test asserts no default disables the guarantee its key governs.
> **And** *(failure path)* a documented key with no backing entry, or a default that disables its own guarantee, fails the build.

1. **AC1 — Configuration is data, with a default per key (AD-24).** A declared schema (`apx/core/domain/config.py`) enumerates every per-*tenant* configuration-as-data key from AD-24's bind list — taxonomy, scopes, model provider & endpoint, configured sources, chunking configuration, exclusion list, cascade share ceiling, off-corpus refusal, interface language. Each key declares a **type**, a **default**, the **guarantee it governs**, and — where it governs a switchable guarantee — a predicate the default must satisfy. Values are stored as data rows (`tenant_setting(tenant, key, value)`), never as code and never as a per-deployment environment variable.
2. **AC2 — One audited surface; every change validated, reversible, recorded (AD-25).** `set_config(tenant, actor, key, value)` is the only write path: it **validates** the value against the declared schema (an unknown key or an out-of-type value is refused with a typed error, never a silent default), **records** an *audit-record* entry carrying actor, key, **before** and **after** and a timestamp (so the change is **reversible** — the before value is on the record, and setting it back restores it), and is **atomic** with that entry. A re-set to the identical value is a no-op that writes no phantom entry. `get_config`/`get_all_config` read every value (stored, or the schema default). A configuration value whose provenance is **not** an audited change through this surface (a direct DB edit) is **detectable** — `config_provenance` reconciles each stored value against the last audited change (or the default) for its key.
3. **AC3 — Provisioning through the surface (AD-25).** `provision_tenant(tenant, admin_email, admin_password, admin_name, scopes, taxonomy)` establishes, in **one audited transaction**, the *tenant*'s **first administrative grant** (an `is_admin` user with their scopes) and its **taxonomy** (seeded as an audited configuration value), and writes a `tenant_provisioned` *audit* entry — so a correctly fail-closed installation has an administrator who can see and grant. It **fails closed** if the *tenant* already has an administrator (no silent takeover of a live firm). Exposed off-line through `python -m apx.manage provision` (the first-run bootstrap; the authed cockpit manages the rest thereafter). It is inside the *tenant* boundary — never cross-*tenant*.
4. **AC4 — No *tenant* identity in a code branch (AD-24, structural).** A static check (`no_tenant_conditional_in_core`) asserts **no conditional anywhere under `core/` reads a *tenant* identifier** — a *tenant* is a filter argument and a row key, never a branch (`if tenant == "cabinet-x"` fails the build). Registered in the one checks artefact every installation runs. Fails closed on an unparseable file; carries a failure fixture.
5. **AC5 — Documented keys exist; no default disables its guarantee (AD-24, structural).** Two build-failing checks: `documented_config_keys_exist` asserts every configuration key named in the documentation (the README config-reference block) exists in the schema (the v1 defect: keys that appeared in zero source files); `config_defaults_preserve_guarantees` asserts every key that governs a switchable guarantee has a default that keeps it **on** (the v1 defect: the off-corpus gate shipped disabled). Each carries a failure fixture that fires.
6. **AC6 — Green and honest.** All existing tests pass; `ruff` + `python -m apx.checks` + `pytest` + fitness green; README documents the configuration surface and its keys; the `mfa_required` toggle is migrated onto the audited surface (no second config path left behind); no SPA/visual over-build (AD-29 deferred), no threshold-consumer over-build (each in its own story).

## Dev Notes

- **Why a generic key→value store, and why `mfa_required` moves into it.** AD-25 is "**one** surface reads and changes **every** configuration-as-data value." A per-key typed column (today's `tenant_config.mfa_required`, edited by a `set_mfa_required` that wrote **no audit entry**) is a second surface and an unaudited write — exactly what AD-25 forbids. So 1.9 folds `mfa_required` into `tenant_setting` and routes it through the audited `set_config`; `mfa_status` reads it back. One store, one write path, one audit shape. [Source: ARCHITECTURE-SPINE.md#AD-24, #AD-25; apx/adapters/store_postgres/store.py:774]
- **The two guarantee-governing keys encode v1's defects.** `off_corpus_refusal_enabled` ships **True** (v1's off-corpus gate shipped disabled by default — "a guess that looked like a proof"), and `cascade_stage3_max_share` ships **< 1.0** (a config widening the uncertain band to *everything* would send the whole corpus to the LLM, the biggest cost/egress of the system — AD-18 makes that a policy escape, not the default). The `config_defaults_preserve_guarantees` check asserts each governing key's default satisfies its predicate, so a future edit that flips a default off turns the build red. Keys that only *tune* (language, endpoint, taxonomy) govern no switchable guarantee and carry no predicate. [Source: ARCHITECTURE-SPINE.md#AD-18, #AD-20, #AD-24; PRD FR-30]
- **Reversibility is the recorded before/after, not a snapshots table.** AD-25 wants a change to be reversible and to carry before→after. Because every value is data and each change records both, reversibility is inherent: read the before off the audit, `set_config` it back. No separate version table is built (that would be the derived-artefact machinery of AD-23, which has no artefacts yet). A test proves A→B→A restores. [Source: ARCHITECTURE-SPINE.md#AD-25]
- **AD-23 staleness is carried as a flag, not wired.** AD-25 says a config change "marks derived artefacts stale (AD-23)". The derived artefacts (ranked order, the line, confidence bound) are epics 4–5; none exist to mark. So `ConfigKey.affects_retrieval` records which keys are staleness-relevant and the audit entry notes it — the hook a future artefact consults. Building a staleness engine now would be over-build against nothing. Recorded so the deferral is a decision. [Source: ARCHITECTURE-SPINE.md#AD-23, #AD-25]
- **Provenance detectability = reconcile rows against the audit.** "A configuration value whose provenance is not an audited change through this surface is detectable as such." `config_provenance` reads the tenant's `config_changed` audit entries (key + after), and flags any `tenant_setting` row whose value matches neither the last audited `after` for that key nor the schema default — i.e. a direct DB edit that skipped the surface. This is the enforceable form of "direct database editing is not the mechanism." [Source: ARCHITECTURE-SPINE.md#AD-25]
- **The tenant-branch check is AD-24's own resolved check.** AD-24 rewrote its behaviour rule to "the real check, which is greppable: no conditional anywhere under `core/` reads a *tenant* identifier." So `no_tenant_conditional_in_core` AST-scans `apx/core/` for an `if`/`match`/ternary whose test compares a *tenant*-named expression (`tenant`, `tenant_id`, `tenant_key`, `tenant_name`) against a constant (or a constant collection via `in`). Core is clean today (verified). A `tenant` is a filter argument and a row key; it is never a branch. [Source: ARCHITECTURE-SPINE.md#AD-24]
- **Documented-keys check needs a decidable doc surface.** "Every key referenced in **any** documentation exists" is undecidable over free prose, so the README carries a marked config-reference block (`<!-- config-keys:start -->`…`<!-- config-keys:end -->`) of backticked key names; the check asserts each ∈ schema. A test also asserts the reverse (every schema key is documented) so the block stays complete. The failure fixture is a doc snippet naming a phantom key. [Source: PRD FR-30/FR-56; AD-24]
- **Provisioning is a bootstrap act, the config surface is authed.** A brand-new tenant has no admin to authenticate, so `provision_tenant` runs off-line (`manage.py`, like `ensure-admin`) and establishes the first admin. Thereafter the authed admin API (`/api/admin/config`, `require_admin`, tenant-from-session) is the surface — inside the tenant boundary, never an operator console (AD-25). [Source: ARCHITECTURE-SPINE.md#AD-25; apx/manage.py:30]
- **What this story does NOT do.** The visual provisioning/config SPA (the story's "UX pass required" note) is deferred with the whole front-end (AD-29 static SPA — no `web/` build is produced in epic 1); the mechanism (data rows + audited surface + checks) is what is testable in CI and is the 1.9 deliverable. Wiring each threshold into its consumer (the cascade share into stage-3 gating, sources into ingestion, chunking into the chunker) lands in the consuming story (epics 2/4/5); 1.9 delivers the surface and the defaults. [Source: ARCHITECTURE-SPINE.md#AD-24 ("the default is configuration-as-data, so being wrong is cheap"), #AD-29; epics.md Story 1.9 UX note]
- **Structural-check + fixture pattern (AD-33).** Reuse the 1.3–1.8 pattern: `CheckResult`, registered in `CHECKS`, explicit `roots`/injectable schema, fail closed on unparseable, fixtures text/AST-only and `ruff`-clean. [Source: apx/checks/tenant_isolation.py, apx/checks/secrets.py]

### Completion Notes

- **The generic key→value store folds `mfa_required` in.** `TenantConfig(mfa_required)` was a second, unaudited config surface (`set_mfa_required` wrote no audit entry) — the exact AD-25 violation. Replaced by `TenantSetting(tenant, key, value)`; `set_mfa_required`/`mfa_status` now delegate to `set_config`/`get_config`, so there is one audited path for every value. Migration 0014 carries existing `mfa_required` values across and drops `tenant_config`. All prior MFA tests stayed green.
- **Two guarantee-governing keys encode the v1 defects, build-checked.** `off_corpus_refusal_enabled` defaults **True** (`preserves_guarantee = v is True`); `cascade_stage3_max_share` defaults **0.5** (`0 < v < 1`). `config_defaults_preserve_guarantees` fails the build if any governing default is switched off.
- **Provenance is real detectability.** `config_provenance` reconciles each `tenant_setting` row against the tenant's audited `config_changed` entries (the audit detail is JSON, parsed structurally — not a fragile `k=v` line, since values are arbitrary JSON). A direct DB insert, and a direct edit of an already-audited key, both surface as `audited=false`. The audit chain that provenance trusts is itself tamper-evident (AD-22).
- **The config-change audit detail is JSON** (`{"key","before","after","retrieval"?}`), `sort_keys` for a reproducible chain. `before`/`after` make a change reversible; `retrieval` is the AD-23 staleness hook (no derived artefact exists yet to mark — carried, not wired).
- **Provisioning is atomic and fail-closed.** `provision_tenant` writes the first admin + scopes + taxonomy + three audit entries in one transaction (seqs 1,2,3 via autoflush), refusing a tenant that already has an administrator. Exposed off-line via `python -m apx.manage provision` (the bootstrap before any admin can authenticate). Smoke-tested end-to-end on SQLite.
- **Encryption allowlist: `tenant_setting.key`/`value` are plaintext, table-qualified.** Config values are operational metadata the admin surface displays in the clear — comparable to the already-plaintext `matter`/`scope` names and less sensitive than a matter (client) name; the audited before/after lives in the encrypted `audit_record.detail`. Allowlisted table-qualified so the generic name `value` is not whitelisted globally.
- **Deliberately deferred:** the visual settings/provisioning SPA (AD-29, with the whole front-end); wiring each threshold into its consumer (epics 2/4/5); AD-23 staleness engine (no artefacts yet). All recorded in the story as decisions.
