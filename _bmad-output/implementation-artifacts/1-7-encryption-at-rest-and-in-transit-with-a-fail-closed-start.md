# Story 1.7: Encryption at rest and in transit, with a fail-closed start

Status: done

## Story

As a firm whose *secret professionnel* is a criminal obligation,
I want everything at rest encrypted and the application to refuse to start without it,
so that a stolen disk or a restored backup yields nothing.

**Scope in one line:** give the storage adapters an **application-layer cipher** (AES-256-GCM, key from the environment, never in source) applied to every at-rest **content-bearing column** — originals' provenance, custodian, extracted-text-derived free text, the *audit record*'s detail, the *failure register*, triage rationales, the TOTP secret — **except the two named searchable surfaces** (the `halfvec` vector column, not built until 2.8, and the **deterministic text index**, which today *is* `piece.full_text`), which are protected by **volume/cluster-level encryption** and asserted by the start-up gate instead; make the DB connection carry TLS in transit; and add **one start-up gate that fails closed on both layers** — a missing/unusable application key **or** an unattested data volume — with **no permissive default and no warning-and-continue**. Prove it with a **seeded-token raw-store inspection** that finds no plaintext token anywhere but the named exception, and a **fail-closed start-up test** covering both layers. **Not** secret rotation / key management (1.8, AD-47), **not** the content-free projection (1.10), **not** backup/restore (1.11).

> The ad-hoc build stores everything as plaintext and starts regardless of configuration. 1.7 turns "the disk happens to be encrypted if the host was set up right" into "the application encrypts the content itself and *refuses to run* unless both encryption layers are in place" — the posture a criminal secrecy obligation actually requires.

## Acceptance Criteria

> **Given** any *tenant* data at rest — originals, extracted text, *chunks*, embeddings, OCR images, the *audit record*, the *failure register*, configuration, staged exports, **When** it is stored, **Then** it is encrypted by the application's storage adapters, in a hosted deployment and a single-machine install alike, **except** the two named searchable surfaces — the vector column and the deterministic text index — which are protected by volume- or cluster-level encryption instead (FR-47 as amended, AD-31/47).
> **And** all network traffic carrying *tenant* data or credentials is encrypted in transit, including between the application and its own stores.
> **And** a seeded-token inspection of the raw stores finds no plaintext token, excluding the two named surfaces, which are asserted differently.
> **And** *(failure path)* a deployment started with encryption disabled, without a key, or with an unencrypted data volume, fails to start — no permissive default, no warning-and-continue, both layers covered by one start-up gate.

1. **AC1 — Everything content-bearing is application-encrypted, by the storage adapter.** A symmetric cipher (AES-256-GCM, 32-byte key from `APX_ENCRYPTION_KEY`, never in source) sits behind a SQLAlchemy column type; every content-bearing column is written as ciphertext and read back as plaintext transparently, on SQLite and PostgreSQL alike. The set: `piece.provenance_path`, `piece.custodian`, `failure.filename` / `.submitted_path` / `.detail`, `audit_record.detail`, `piece_label.rationale`, `user_account.mfa_secret`. Routing/identity keys (`tenant`, `matter`, `scope`, `email`, content hashes, ids) and categorical audit metadata (`actor`, `action`, `chain`, `seq`) stay queryable and are **not** document content.
2. **AC2 — The two named surfaces are the only exceptions, stated explicitly.** `piece.full_text` — which the deterministic exhaustive search (`search`, FR-13) runs an SQL `ILIKE` over — **is** the "deterministic text index" of AD-31 in this increment; it and the future `halfvec` vector column (2.8) are the only columns left un-application-encrypted, protected instead by the start-up gate's volume attestation. The exclusion is **named in the seeded-token test with the AD-31 citation**, so nobody reads it as an oversight and nobody weakens the test to accommodate it. (When 3-2 builds a *separate* deterministic index, the stored full text moves inside the application-encryption boundary and the index remains the exempt surface — recorded here so the split is not silently dropped.)
3. **AC3 — Encrypted at rest is proven by a seeded-token raw-store inspection.** A test seeds a distinctive token into every content-bearing field (and a fake TOTP secret), persists, then reads the **raw** column bytes (bypassing the ORM) and asserts the token appears in **no** store **except** `piece.full_text` — where it asserts the token *is* present (proving the exception is a deliberate carve-out, not a silent encryption failure). The audit chain still verifies after a round-trip through the encrypted `detail`.
4. **AC4 — In transit.** `database_url()` honours `APX_DB_SSLMODE` (default `require` for a TCP PostgreSQL host; a same-machine loopback/socket may be set `disable` with a documented rationale) so app↔store traffic is TLS; the browser edge is already HTTPS (HSTS, `APX_COOKIE_SECURE`). Credentials are never in the URL in source (AD-47, unchanged).
5. **AC5 — One start-up gate, fail-closed on both layers.** `startup_gate()` refuses to start (raises, no serve) when the application key is missing/malformed/wrong-length **or** the data volume is not attested encrypted (`APX_VOLUME_ENCRYPTED`). No permissive default, no warning-and-continue; wired into the FastAPI `lifespan` so a real boot exercises it. A unit test drives each fail-closed branch and the pass path.
6. **AC6 — Structural checks (AD-33).** A static check asserts the enumerated content-bearing columns use the encrypted type **and** that `piece.full_text` is *not* encrypted (the named exception — so a future edit can neither silently leave a new sensitive column plaintext nor accidentally encrypt the search surface and break FR-13); a second asserts `startup_gate` references both layers and raises (cannot be silently downgraded to a warning). Both fail closed on unparseable input; registered in the harness with failure-path fixtures.
7. **AC7 — Green and honest.** All existing tests pass (an autouse fixture provisions the test key + volume attestation so the gate and the encrypted columns are exercised suite-wide); `ruff` + `python -m apx.checks` + `pytest` + fitness green; the README documents the encryption posture and the two named exceptions; no key-rotation (1.8), projection (1.10) or backup (1.11) over-build.

## Dev Notes

- **The one genuinely hard reconciliation is the searchable surface — and AD-31 already decided it.** `search` (FR-13) runs `func.lower(piece.full_text).like(...)` — an SQL scan over `full_text`. A randomised cipher makes SQL `ILIKE`/equality over a column impossible, so an application-encrypted `full_text` would break exhaustive search outright. AD-31 anticipates exactly this: the **deterministic text index** is one of the **two named exceptions**, protected by volume-level encryption and asserted by the start-up gate, *because* "neither can be indexed as ciphertext." In this increment `full_text` **is** that index (the standalone index of 3-2 is not built yet), so it is the exempt surface. This is the same shape as 1.3's scope/custodian reconciliation: follow the AD's *rule*, name the exception explicitly in the test, and record the future split. [Source: ARCHITECTURE-SPINE.md#AD-31; apx/adapters/store_postgres/store.py#search]
- **What can and cannot be encrypted, and why.** Randomised AES-GCM ciphertext cannot be matched, ordered or grouped in SQL. So the encrypted set is exactly the **content-bearing, not-queried-by-value** columns (AC1). Routing/isolation keys (`tenant`/`matter`/`scope`), the login key (`email`), the pseudonymous hashes (`content_hash`/`text_key` — one-way already), ids, and categorical audit metadata (`actor`/`action`/`chain`/`seq`) stay plaintext: they are the query surface and the isolation spine, not tenant *document* content. `audit_record.detail` (which carries emails, IPs, counts, subjects) **is** encrypted; the chain is computed over the plaintext `detail` before the column encrypts it, and `read_audit` decrypts before recomputing, so tamper-evidence survives (proven in AC3). [Source: apx/adapters/store_postgres/store.py#_append_audit, #read_audit]
- **Two ORDER BYs touch `provenance_path`.** `labels` and `search` order by it; once encrypted, SQL ordering is meaningless. Order by `piece.id` (plaintext PK, deterministic) in SQL and sort by decrypted provenance in Python. For `search` this changes only the *tie-break of which page is returned under a cap* (id-order rather than path-order); the exhaustive guarantee — honest `total`, every hit a real match — is unchanged. Everything else that reads these columns pulls them into a dict/excerpt with no SQL predicate, so it is transparent. [Source: apx/adapters/store_postgres/store.py#labels, #search]
- **`cryptography` is the dependency, and it is clean.** No AES in the stdlib; `cryptography` (AES-256-GCM) is the standard, well-audited choice — a **local** crypto library, not a hosted-provider SDK, so the egress deny-list (AD-45: `supabase/boto3/google/vercel`, `openai`) does not touch it, exactly as `pwdlib`/`pyotp` are untouched. Used from `core.domain.crypto` alongside `auth.py`'s existing `pwdlib` import (the domain-purity contract is deferred to 1.12 and today allows local libs). [Source: pyproject.toml#tool.importlinter; apx/core/domain/auth.py]
- **The volume attestation is honest about its limits.** The application cannot portably *prove* the block device is encrypted from inside a container, so the second layer is an explicit, **non-default** operator attestation (`APX_VOLUME_ENCRYPTED`) — the same deployment-attestation pattern already used by `APX_COOKIE_SECURE`/`APX_TRUST_FORWARDED_FOR` — that must be backed by real dm-crypt/LUKS on the single-machine install or provider-managed volume encryption in the hosted tier. The cryptographic teeth are the **application-layer key gate**, which is real and tested; the volume flag closes the second layer AD-31 names and refuses a permissive default. Recorded plainly so a reviewer sees the scoping, not a hidden weakness. [Source: ARCHITECTURE-SPINE.md#AD-31; apx/api/app.py#_cookie_secure]
- **No migration.** `EncryptedText` stores base64 in the same physical `TEXT`/unbounded-`VARCHAR` columns (ciphertext fits — the encrypted columns are all unbounded), and Alembic migrations are hand-written DDL, not `metadata.create_all` — so the ORM type change needs **no** DDL delta and the CI `db` job (upgrade→downgrade→upgrade) is unaffected. Enabling encryption assumes a **clean store**: a pre-existing plaintext value in an encrypted column now fails closed on read (by design). The demo store is re-provisioned; no client corpus exists. [Source: apx/adapters/store_postgres/migrations/]
- **Start-up gate mechanics.** A pure `startup_gate(env)` (unit-testable per branch) wired into the FastAPI `lifespan`, not module import — so `from apx.api.app import app` stays importable in collection, while `with TestClient(app)` (the context-manager form the API tests already use) exercises the gate. An autouse `tests/conftest.py` fixture provisions the key + volume attestation suite-wide (realistic — tests *should* run with encryption on); the gate tests pass an explicit `env` dict to drive the fail-closed branches without disturbing the global. [Source: tests/api/test_ingest_api.py]
- **Structural-check + fixture pattern (AD-33).** Reuse the 1.3–1.6 pattern: `CheckResult`, registered in `CHECKS`, explicit `roots`, fail closed on unparseable, fixtures AST-parsed only and `ruff`-clean. [Source: apx/checks/credential_storage.py]
- **Testing standards.** Seeded-token inspection and gate tests run on SQLite everywhere; raw-store reads use a driver-level `SELECT` to see ciphertext past the ORM. Tests unreachable from runtime (AD-16). [Source: tests/adapters/test_session_store.py]

### Deliberately deferred (documented, not fixed)

- **Real device verification of the data volume** (vs the operator attestation). The app cannot portably prove block-device encryption from inside a container; the attestation is the honest, portable second layer, and finding #1 removed the permissive default so it is now a conscious act. Real verification (inspect dm-crypt/LUKS, or a provider marker) belongs to the deploy/DR story (1.11). **Accepted risk**, recorded.
- **`sslmode=verify-full`** (server-authentication, not just encryption) — defaulting it needs a CA bundle that would break the simple case; `require` (encrypt-in-transit) is the MVP baseline, hardened at the deploy layer. Named, not silently chosen.
- **`search` capped subset tie-breaks on `piece.id`** (provenance is ciphertext) rather than provenance — `total` and the all-hits-match guarantee are unchanged; documented in the code and story.
- **Random-nonce ceiling** (~2³² values/key) — an INFO note for the key-rotation story (1.8), irrelevant at MVP scale.
